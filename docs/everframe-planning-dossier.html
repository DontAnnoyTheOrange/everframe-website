Everframe website: requirements, design and plan

Nothing here is built yet. This is the analysis you approve before any database or app code is written. Items tagged DOC come from your feature document. Items tagged REC are my recommendations or assumptions.

1. Executive summary

What the document asks for. A dark, cinematic, scroll-driven photography site for event coverage in the Philippines (weddings, debuts and 7th birthdays, corporate events, concerts). The homepage is a chaptered story: shutter load-in, hero with two calls to action, studio introduction, featured work as full-viewport category pages, a four-step client journey (Inquire, Plan, Shoot, Deliver), three packages, social proof, services, and a closing contact block.

Booking gets its own page at /booking, reached from a pricing calculator or directly from the nav. A separate light-themed admin tool shows the same bookings table as a sortable schedule, with a + New booking button for requests that arrive by Messenger or phone. Statuses named in the document: inquiry, pending_confirmation, confirmed.

What you already have. The zip contains a Next.js scaffold: a brand loading screen (black, bone #F5F1EA, brass #C9A24B, EF monogram with shutter icon), a placeholder hero, Tailwind 4, Framer Motion. It is a start, not the design: the hero has no real imagery and no routes exist.

Scaffold issues found.
  • The loader forces an 8 second minimum. The document says "brief". I recommend about 2 seconds, shown once per session.
  • globals.css still sets a white background and Arial. The public theme needs dark tokens and the chosen fonts.
  • The hero copy says "photography and videography". The document only describes photography. See decision 5.
  • Versions pinned in package.json trail the registry as of today (Next 16.3.0 vs 16.4.2, React 19.2.8 vs 19.3.1, Framer Motion 13 vs 14.3). I will re-verify and pin at Phase A.
  • Nothing in the scaffold uses the Supabase, Cloudinary, Zod or lightbox packages yet.

Limit of this review. I could read the document's text. The UI mockups in it are images and did not come through as readable content, so layout details (exact card contents, calendar design, admin columns) are taken from the written descriptions only. If any mockup contradicts this plan, tell me which one.

4. Architecture

Roles of each service

Supabase (keep)

PostgreSQL, Auth and RLS. Source of truth for bookings, schedule, packages, add-ons, categories, project and image metadata, testimonials, settings, admin roles. Free tier adequate. Downside: free projects pause after inactivity, and backups are limited.

Cloudinary (keep)

Stores and transforms the image files. The database stores only the public ID, dimensions, alt text and order. Free tier is enough to start. Secret stays on the server; uploads use a server-signed request.

Sanity (drop)

It would be a second place to edit portfolio content, and the admin dashboard you require already does that. Dropping it avoids duplicate sources of truth, another login, and another bill. Reconsider only if you later want rich editorial pages.

Vercel + GitHub (keep)

Hosting, preview deployments, environment secrets. Free Hobby plan is for non-commercial use; a paid business site may need Pro. Check Vercel's current terms before launch.

Framer Motion (keep)

Reveal and scroll animation. Used sparingly, with reduced-motion fallback.

Lenis (skip) and lightbox

Lenis changes native scroll and can fight scroll-snap, anchors and accessibility. Your featured-work chapter relies on scroll-snap, so skip it. Lightbox: yet-another-react-lightbox, which is React-native with zoom, captions and keyboard support. PhotoSwipe is fine but needs more glue. BlurHash dropped: Cloudinary can serve a tiny blurred version, so no extra package or column.

Why each table exists

TablePurpose and key rules
admin_usersWhitelist of who is an administrator, keyed to the Supabase auth user. No public insert policy. Replaces a "profiles" table because there is no public user profile in this app.
event_categoriesWedding, Debut/7th birthday, Corporate, Concert. Used for homepage panels, services cards, portfolio filters and booking event type. Deleting is restricted while projects or bookings reference it; use is_published=false instead.
portfolio_projectsOne gallery (a shoot). Belongs to one category. Public sees only is_published.
portfolio_imagesImage metadata and Cloudinary public ID. Cascade delete with project. Unique (project_id, sort_order) deferrable for reordering; partial unique index allows only one cover per project.
packagesBasic, Standard, Premium: starting price, included hours, extra-hour rate, inclusion list. Check: prices and hours at least 0.
addonsOptional extras, flat or per hour.
bookingsSingle table for website, Messenger and phone bookings, with source. Price and package details are copied in as snapshots. Checks: ends_at > starts_at; status in the allowed list; contact fields required except for admin-created rows. Exclusion constraint on confirmed rows (section 9).
booking_addonsMany-to-many between bookings and add-ons, with price snapshots per line.
booking_status_historyAppend-only audit of status changes; supports "follow-up" metrics.
availability_blocksAdmin-made unavailable ranges (day off, personal commitment). Separate from bookings because a block has no client or price.
testimonialsQuotes shown on the homepage; optional link to a category.
site_settingsKey/value JSON for Messenger link, email, socials, service area, stats, turnaround, buffer minutes, hero text.

Relationships in plain language

  • One-to-one: an auth user has at most one admin_users row.
  • One-to-many: category to projects; project to images; category and package to bookings; booking to its add-on lines and its status history; admin to blocks.
  • Many-to-many: bookings and add-ons, through booking_addons.
  • Bookings reference packages and categories with ON DELETE RESTRICT, so a package used by a booking cannot vanish. Packages are retired with is_active=false.
  • Price changes: the booking stores its own name, base price, extra-hour rate and add-on prices at creation. Editing a package later changes only future quotes.
  • Blocks and bookings are different tables but one rule: any new confirmed booking or block is checked against both, under one lock, so they cannot overlap.
  • No orphans: foreign keys everywhere; images cascade with their project; Cloudinary files are removed by a server step (section 8, diagram 3).

Each package is a flat price for an hour range (min_hours, max_hours), so the table stores both instead of one base-hours value. Hours outside a range (for example 5 hours, or more than 8) are a custom quote: the request is accepted with no total, and you set the price when you review it. The same formula lives in one place: a Postgres function that reads current rows and returns an itemised breakdown. The calculator calls it for previews; the booking function calls it for the stored total. The browser's number is never used.

Preventing double booking

  1. Occupancy range: tstzrange(starts_at - buffer, ends_at + buffer), buffer from settings.
  2. Transaction lock: booking and status functions take pg_advisory_xact_lock on a fixed key, so two simultaneous requests are processed one at a time. This single lock covers both tables (bookings and blocks), which a plain constraint cannot do across tables.
  3. Check inside the lock: look for overlapping rows in confirmed bookings and availability_blocks; refuse if any.
  4. Safety net: a GIST exclusion constraint on bookings, active only where status is confirmed, so even a buggy code path cannot create two overlapping confirmed rows.
  5. Public calendar: a function returns only busy time ranges, with no names or contact data.
  6. Time zones: everything stored as timestamptz; interpreted in Asia/Manila; date-only UI converts using that zone.

Policy for pending requests: several clients may request the same open slot. The admin sees them flagged as overlapping and confirms one; confirming runs the lock-and-check above, so the others can only be rejected. This keeps the public calendar honest without letting strangers block your dates with unconfirmed requests.

10. Security plan

Authorization model

A protected admin_users table plus a SECURITY DEFINER function is_admin() with a fixed search_path. Policies call it, which avoids recursive policies. JWT custom claims were considered; they are fast but stay valid until the token expires, so revoking an admin is slower. With one or two admins, the table is simpler and revokes instantly.

First admin

Create the user in Supabase dashboard (Authentication, Users), with public sign-ups turned off. Then run one SQL insert in the SQL editor adding that user's id to admin_users. No app code can do this, and no policy lets a user insert themselves.

RLS access matrix

Anon: select published categories, projects, images, active packages and add-ons, published testimonials, public settings. Nothing on bookings, blocks, history or admin_users. Admin: full access to everything through is_admin(). Booking creation: only through a function; direct insert on bookings is not granted to anon.

Public booking endpoint

Server Action validates with Zod, rate-limits by IP, includes a honeypot field (Cloudflare Turnstile is an option if spam appears), then calls the function with the server-only key. Execute on that function is revoked from anon and authenticated roles.

Uploads

Admin-only signed upload; allowed formats and a size cap enforced in the signature parameters and re-checked after upload; Cloudinary secret server side only.

Other controls

Security headers via next.config; cookies httpOnly through @supabase/ssr; generic login errors; no service-role import in client files (enforced with the server-only package); dependency audit before launch.

RLS testing: three sessions in the test suite: no login, a logged-in user not in admin_users, and an admin. Each runs a list of reads and writes with expected pass or fail. Nothing is declared secure until those tests run.
